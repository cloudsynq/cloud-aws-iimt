01

What is Amazon S3?

Amazon S3 (Simple Storage Service) is AWS's object storage service. It lets you store and retrieve any amount of data — files, images, videos, backups, logs — from anywhere in the world over the internet.

Simple Analogy
Think of S3 as a giant digital locker room in the cloud. Each locker is a Bucket. Inside each locker, you can store anything — files, images, videos. Anyone with the right key can open the locker and access the items. You can have as many lockers as you need, and each can store an unlimited amount of stuff.

Why is S3 So Popular?

  • Unlimited storage — no capacity limit, store as much as you want
  • 99.999999999% durability (11 nines) — AWS automatically keeps multiple copies of your data
  • Global access — access your files from anywhere via a URL
  • Pay as you use — no upfront cost; you pay only for what you store and transfer
  • Any file type — images, videos, PDFs, zips, logs, code — anything
  • Integrates with everything — EC2, Lambda, CloudFront, RDS — almost every AWS service uses S3

Common Use Cases

  • Storing images and videos for websites
  • Hosting static websites (HTML, CSS, JS)
  • Database backups and disaster recovery
  • Storing log files and analytics data
  • Build artifacts in CI/CD pipelines (store compiled code)
  • Data lake for big data and machine learning
S3 is a Global Service
S3 is not tied to a specific region when you access it — but each bucket is created in a specific region where data is physically stored. The bucket's URL is global; the storage location is regional.
02

Buckets & Objects

S3 has two main concepts: Buckets (the containers) and Objects (the files inside).

Buckets

A Bucket is a top-level container for storing objects. Think of it as a folder in the cloud.

  • Bucket name must be globally unique across all AWS accounts worldwide
  • Name must be lowercase only, no spaces, 3–63 characters
  • Each bucket belongs to one specific AWS Region
  • One AWS account can have up to 100 buckets by default (can request more)
  • Bucket names cannot be changed after creation — choose carefully!
Bucket URL Format
Every object in S3 gets a unique URL:
https://bucket-name.s3.region.amazonaws.com/filename.jpg

Example: https://iimt-college.s3.ap-south-1.amazonaws.com/photo.jpg

Objects

An Object is a file stored inside a bucket. Every object has:

ComponentWhat it isExample
KeyThe file name / path inside the bucketphotos/2024/pic.jpg
ValueThe actual file data (content)The image bytes
MetadataExtra info about the object (type, size, tags)Content-Type: image/jpeg
Version IDUnique ID if versioning is enabledabc123xyz

Object Size Limits

  • Maximum object size: 5 TB
  • Maximum single upload: 5 GB
  • For files larger than 100 MB → use Multipart Upload (splits file into parts)
S3 is NOT a File System
S3 does NOT have real folders. The / in a key like photos/2024/pic.jpg is just part of the file name. The AWS Console shows them as folders, but they don't actually exist — it's just a visual trick. S3 is a flat key-value store.

S3 Storage Classes

S3 offers different storage classes to balance cost vs. how often you access the data. You choose the class based on how frequently you need to access the files.

Simple Analogy
Storage classes are like different types of bank accounts. A savings account (Standard) — easy to access but costs more to maintain. A fixed deposit (Glacier) — your money is locked, you pay a penalty to withdraw early, but the interest rate is lower.

Access Control — Who Can Access What

By default, S3 buckets and objects are completely private. Nobody except the bucket owner can access anything. You control access using these tools:

1. Block Public Access (Master Switch)

This is a safety switch at the account or bucket level. When enabled (which is the default), it overrides everything and prevents any public access — even if you set a bucket policy that allows it.

Always Keep This ON
Block Public Access should be ON for any bucket with sensitive data. Only turn it OFF for buckets that need to be truly public (like a static website or public image CDN).

2. Bucket Policy (JSON)

A Bucket Policy is a JSON document that controls who can access the bucket and what they can do. It works at the bucket level (applies to the whole bucket and all objects inside).

ElementMeaning
PrincipalWHO the policy applies to (* = everyone, or specific IAM user/role ARN)
ActionWHAT they can do (s3:GetObject, s3:PutObject, etc.)
ResourceWHICH objects the rule applies to (bucket ARN)
EffectAllow or Deny

3. ACL — Access Control List

ACLs are an older method of controlling access at the object level. AWS now recommends using Bucket Policies instead of ACLs for most use cases.

Access Decision Flow

  1. Is Block Public Access ON? → If yes, deny all public access (end of story)
  2. Is there an explicit Deny in the Bucket Policy or IAM policy? → Deny
  3. Is there an explicit Allow in the Bucket Policy or IAM policy? → Allow
  4. Default: Deny
05

Pre-signed URLs — Temporary Access

A Pre-signed URL is a temporary URL that gives anyone access to a specific private S3 object for a limited time. After the time expires, the URL stops working.

Simple Analogy
Imagine you want to share a document from a locked office. Instead of giving someone the office key (permanent access), you give them a temporary visitor pass that expires in 2 hours. They can enter, get the document, and leave. After 2 hours, the pass becomes invalid. That is a Pre-signed URL.

How It Works

  • Only the bucket owner (or someone with access) can generate a pre-signed URL
  • The URL contains an encrypted signature and expiry time
  • Anyone with the URL can access the object — no AWS account needed
  • After expiry, the URL returns a 403 Forbidden error
  • Maximum expiry: 7 days (604800 seconds)

When to Use Pre-signed URLs

  • Share a private file download link with a customer temporarily
  • Allow a user to upload a file directly to S3 without AWS credentials
  • Streaming private video/audio for a limited time (e.g., after payment)
Azure Equivalent
Pre-signed URL in AWS S3 = SAS Token in Azure Blob Storage. Both provide temporary, time-limited access to private files.
06

S3 Versioning

Versioning keeps multiple versions of the same object. Every time you upload a new version of a file with the same name, S3 keeps the old version too — nothing is deleted.

Simple Analogy
Think of versioning like Microsoft Word's track changes or Google Docs version history. Every save creates a new version. You can go back to any previous version at any time. Nothing is permanently lost.

How Versioning Works

  • Versioning is disabled by default — you must enable it per bucket
  • Once enabled, it cannot be fully disabled — only suspended
  • Each version gets a unique Version ID
  • When you "delete" an object, S3 adds a Delete Marker instead of actually deleting it — the old versions are still there
  • To permanently delete all versions, you must delete each version individually
ActionWithout VersioningWith Versioning
Upload file.txt (v2)Overwrites old file — gone foreverOld v1 saved, new v2 becomes current
Delete file.txtGone foreverDelete marker added, all versions preserved
Recover old versionNot possibleRestore any previous version by Version ID
Versioning Increases Storage Cost
Every version of every file is stored and billed separately. A file updated 10 times = 10 versions all charged. Use Lifecycle Policies (Section 08) to automatically delete old versions after a set number of days.
07

Static Website Hosting

S3 can host a static website (HTML, CSS, JavaScript files) without needing a web server like Apache or Nginx. S3 serves the files directly to the browser.

Static vs Dynamic Websites
Static = HTML/CSS/JS files only. Content is the same for everyone. Can be hosted on S3.
Dynamic = Requires a server to generate content (PHP, Python, Node.js). Cannot be hosted on S3 alone — needs EC2 or Lambda.

How to Enable

  1. Create an S3 bucket with the same name as your domain (e.g., www.mysite.com)
  2. Upload your index.html and other files
  3. Enable Static Website Hosting in bucket properties
  4. Set index document: index.html, error document: error.html
  5. Make the bucket public (set Bucket Policy to allow s3:GetObject for everyone)
  6. Your site is live at: http://bucket-name.s3-website-region.amazonaws.com

Real Use Cases

  • Portfolio websites, landing pages, documentation sites
  • Paired with CloudFront (CDN) for fast global delivery + HTTPS
  • Paired with Route 53 (DNS) for custom domain names
  • React / Vue / Angular apps (after build, output is static files)

S3 Lifecycle Policies

A Lifecycle Policy automatically moves or deletes objects based on rules you set. You define: "After X days, move this object to a cheaper storage class. After Y days, delete it."

Simple Analogy
Think of it like a file cabinet cleanup rule: "Active files stay on the desk (Standard). After 30 days, move them to the cabinet (IA). After 90 days, put them in the basement (Glacier). After 365 days, shred them (delete)."

Use Cases

  • Log files — keep 30 days active, archive for 6 months, delete after 1 year
  • Database backups — move to Glacier after 90 days, delete after 7 years
  • Versioning cleanup — delete non-current versions after 30 days to save cost

S3 Replication

S3 Replication automatically copies objects from one bucket to another. There are two types:

CRR — Cross-Region ReplicationSRR — Same-Region Replication
What it doesCopies objects to a bucket in a DIFFERENT regionCopies objects to a bucket in the SAME region
Use caseDisaster recovery, lower latency for global usersLog aggregation, separate account backups
RequirementVersioning must be ON in both bucketsVersioning must be ON in both buckets
CostData transfer fees apply (across regions)No data transfer fees
Key Point for Exams
Replication only applies to new objects added after replication is enabled. Old existing objects are NOT automatically replicated. Use S3 Batch Operations to replicate existing objects.

S3 Encryption

S3 encrypts your data to protect it. Encryption happens in two places:

Encryption at Rest (data stored in S3)

TypeWho Manages KeysDetails
SSE-S3AWS manages everythingDefault. AWS generates and manages the keys. Simplest option.
SSE-KMSAWS KMS manages keysYou control who can use the key. Audit trail via CloudTrail.
SSE-CYou manage the keysYou provide the key with every upload/download request.
Client-SideYou encrypt before uploadData is encrypted on your side before sending to S3.

Encryption in Transit

Use HTTPS when uploading/downloading. S3 supports both HTTP and HTTPS — always use HTTPS to protect data while it travels over the internet. You can enforce HTTPS via a Bucket Policy.

Default Encryption
Since January 2023, all new objects in S3 are encrypted by default using SSE-S3 (AES-256). You don't need to do anything extra — it's automatic.

Key Summary

Everything You Must Remember About S3

S3 = object storage for any file type, unlimited size
Bucket name must be globally unique (worldwide)
Objects have a Key (name), Value (data), Metadata
Max object size = 5 TB; use Multipart for files > 100 MB
S3 is NOT a file system — no real folders, just key names
Buckets are private by default — Block Public Access is ON
7 storage classes: Standard → Intelligent → IA → One Zone-IA → Glacier × 3
Pre-signed URL = temporary access link with expiry
Versioning = keeps all versions of every file; can't be undone once enabled
Lifecycle Policy = auto-move to cheaper storage after X days
CRR = copy to different region; SRR = copy within same region
Default encryption = SSE-S3 (AES-256) since Jan 2023
S3 can host static websites (HTML/CSS/JS only)
11 nines = 99.999999999% durability (virtually impossible to lose data)
